================================================================================
ORIKASERVER STARTUP-FAILURE CODE AUDIT
================================================================================

Date:       2026-05-13
Symptom:    OrikaServer.exe launches, appears briefly in tasklist, then exits
            silently. No error_log.txt written, no Windows Event Log entry, no
            crash dump on disk, no new D:\logs\<date>.log file.
Method:     3 parallel review agents across MFC startup path, init/factory/
            connection code, and recently-committed audit fixes.
Auditor:    Claude (Opus 4.7, 1M context).

--------------------------------------------------------------------------------
TOP SUSPECTS FOR THE SILENT-EXIT SYMPTOM (ranked by likelihood)
--------------------------------------------------------------------------------

These are the findings that best match "process briefly appears in tasklist then
disappears with zero logs anywhere":

  #1  D1 - StackReserveSize=500 GB in Debug|x64 vcxproj. PE loader rejects this
          and terminates the process before any C++ code runs. (Only affects
          Debug|x64; Release|x64 has 100 MB which is excessive but bootable.)

  #2  A2 - OpenSSL link/runtime version mismatch. Project links against import
          libs that resolve to libssl-1_1-x64.dll while x64/Release/ ships
          libssl-3-x64.dll. OS loader can't find the imported DLL, kills the
          process before WinMain. Verify with `dumpbin /dependents
          x64\Release\OrikaServer.exe`.

  #3  I1 - `FILE _iob[] = { *stdin, *stdout, *stderr };` static initializer in
          openssl_iocp.cpp:12-16 dereferences stream globals at C++ static-init
          time. If the linked OpenSSL/MT5 import libraries expect a different
          UCRT than the one currently linked, stdin/stdout/stderr may be NULL
          and dereferencing them faults before WinMain.

  #4  D2 / A1 - Debug|x64 config flipped to Release-flavour: defines NDEBUG
          (not _DEBUG), links the release CRT (MultiThreadedDLL, not
          MultiThreadedDebugDLL). MFC chooses mfc140u.dll vs mfc140ud.dll based
          on _DEBUG; mismatched CRT/MFC pairs cause STATUS_DLL_NOT_FOUND silent
          exit on machines missing the matching redistributable.

  #5  I2 / A3 - `exit(3) / exit(4) / exit(5)` in `ssl_set_ctx_cert_and_key` when
          Certificate.pem or key.pem can't be loaded from CWD. ERR_print_errors_fp
          writes to stderr which is detached for /SUBSYSTEM:WINDOWS. Reachable
          AFTER the user clicks Start, especially because CLogFile::CreateDirectories
          calls _chdir("..") 20 times (audit D9 / now I3 cross-ref) and may have
          corrupted CWD by the time cert load runs.

  #6  I8 - CLogFile() default ctor leaves `m_pLogFile` uninitialised. First
          LogEvent goes through ChangeFile -> CloseFile -> fclose(garbage). In
          a Release-flavour Debug binary (point #4) this is a near-immediate
          crash on the very first log line attempted from startup.

  #7  I6 - LoadConfigFile stores dangling LPCSTR (from a CStringA temporary)
          into CStaticClass::dataFeedServer / GatewayServer statics. Runs from
          OnInitDialog. Subsequent reads dereference freed memory.

--------------------------------------------------------------------------------
SEVERITY LEGEND
--------------------------------------------------------------------------------

  CRITICAL  Plausibly causes the observed silent exit; fix before next attempt.
  HIGH      Real bug; may or may not be the launch killer; should fix.
  MEDIUM    Latent issue; not THE cause but worsens diagnostics or correctness.
  LOW       Style / fragility / future-proofing.
  INFO      Verification result (e.g., audit fix confirmed safe).

ID: D1
SEVERITY: CRITICAL
TITLE: Debug|x64 link config sets a 500 GB main-thread stack reserve
FILE: OrikaServer/OrikaServer.vcxproj:134
CODE:
  <Link>
    <SubSystem>Windows</SubSystem>
    ...
    <StackReserveSize>500000000000</StackReserveSize>
  </Link>
WHY:
  PE-header SizeOfStackReserve set to ~500 GB. Windows refuses to reserve that
  much virtual memory for the main thread (or rejects the value as invalid),
  terminating the process before WinMain runs. No error log, no event entry.
  Exactly matches the symptom for Debug|x64 builds.
FIX:
  Remove the element (default 1 MB) or set:
    <StackReserveSize>1048576</StackReserveSize>
  Same fix needed for Release|x64 at line 194 (currently 100,000,000 ~100 MB —
  bootable but excessive).

TITLE: _iob[] static initializer dereferences stdin/stdout/stderr at process load
